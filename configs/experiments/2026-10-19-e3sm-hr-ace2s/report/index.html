HR ACE2S Bring-up

Updated 2026-10-20 05:49 · allocations 60022811 + 60023253 (10-19) and 60032495 (10-20)

Current answer (2026-10-20)

Cutting the spherical harmonics is not needed. The full-harmonics model (2.1 B params, all 720 modes) now trains end to end on one node with 4×1 tiles at 0.245 samples/s (~4.1 s/step). Before, it ran out of memory. The memory went to things that were replicated on every tile: weights, gradients, DDP buckets, EMA and Adam state, plus duplicate SHT tables. Three committed fixes (sharded Adam via shard_optimizer_state, gradient_as_bucket_view, shared SHTs) bring the steady-state peak from 71.7 to 57 GB in the benchmark. A prototype that also shards the spectral weights by l and pos_embed by tile reaches 35 GB, runs 4% faster, and fits a wider embed-512 model at 44 GB.

Communication within a node is cheap; across nodes it is not. At 4×1 tiles on one node, transposes and gradient sync are 9% of the step for the 0.5-modes model (14% at full modes); the split compute itself is at ideal. 1×4 costs 16% and 2×2 37%, because they pay the azimuth transposes too. Across nodes, all-to-all runs at ~31 GB/s per GPU against ~200 on NVLink, so splitting one sample over 2–4 nodes spends 35–48% of the step communicating. Data-parallel replicas across nodes cost nothing (2.53–2.54 s/step on 1, 2 and 4 nodes).

Recommended layout: 4×1 tiles per node, data parallelism across nodes. 4×1 also beats 2-GPU tile groups per node by 4–14% in throughput. Exact per-GPU memory is in the “Memory budget” section, for node planning.

Earlier results still hold: end-to-end training, validation, inference and resume work; 8 nodes are about 37 h for 20 epochs at 0.5 modes. At full modes it is ~1.7× that until the weight sharding lands.

What was wrong, and what changed

  1. Inter-node NCCL used TCP. The uv venv’s torch ships its own NCCL with no Slingshot plugin. An 8.4 GB all-reduce over 2 nodes measured 2.2 GB/s bus bandwidth; with NERSC’s aws-ofi-nccl plugin it measured 67.8 GB/s. A 2-node step of the baseline took 18.2 s against 5.6 s on one node. scripts/nccl-ofi.sh fixes this. The hist campaign pays this too: its 1° model (0.46 B params) across 2 nodes runs 0.873 s/step on TCP against 0.782 with OFI, 12% slower, all of it in backward. Adding the plugin to the hist sbatch scripts should speed those runs by about 10%.
  2. netCDF-C reads CDF-5 files 8 KB at a time. strace showed 1,018 read() calls of 8,192 bytes for two 4 MB fields. Reads ran at 30–105 MB/s per reader against 1.2 GB/s raw. The new engine: cdf5 issues one pread per field and is bit-identical to netcdf4. A loader sample reads at a median ~750 MB/s. Commit b9cb5a08c.
  3. Spatial gradient sync was unbucketed. Each parameter had a hook that cloned its gradient and ran a blocking all-reduce. It is now one DDP over the world with a sum-over-tiles, mean-over-replicas comm hook. This makes no difference on one node (NVLink); it is for multi-node runs. Commit dabfe58a9.
  4. EnsembleLoss was tile-local. CRPS gradients were H·W× serial. The energy score was mis-scaled by about √(H·W), so at 2×2 the 0.9/0.1 mix trained as roughly 0.9/0.05. The logged loss, and the best-checkpoint selection that uses it, came from rank 0’s tile only. The corrector’s in-graph global means also dropped cross-tile gradient terms. All now match serial on every rank. Commit 88d85d5fb.
  5. Inline inference rejected valid runs. The number of initial conditions had to divide the world size instead of the data-parallel size. Commit 1b1f7391d.
  6. The spatial backend ignored the collective timeout and used torch’s 10-minute default. Ported from the hist branch and extended to that backend. Commit 8e41193f0.
  7. Every spatial rank read the full sample. Each rank now loads only its own tile, bit-identical to the old path. A 4×1 latitude band reads 2.6× faster, with 4× less host memory, pinned memory and H2D traffic. In an end-to-end A/B, the training losses matched the old path exactly at every logged step, and node RAM in use peaked at about 41 GB above idle against ~150 GB in use before. Commit 88a70581d.
  8. torch-harmonics leaked about 12 GB of host RAM per rank. Its lru_cache keeps every fp64 Legendre table (~3 GB each at lmax 720) for the life of the process. With 4 ranks per node, the first training start was OOM-killed during model build. fme now clears that cache after building each SHT. A CPU build drops from 21.3 to 9.4 GB RSS. Commit b14fe7a4d.

Six loader and logging commits were also ported from the hist branch. They provide rename, reference_pressure_name, frozen-precipitation naming, the time-mean plot_variables, the val mean_map N× fix and the logging basicConfig.

Within a node, ~40% of each transpose is torch-harmonics’ split/contiguous/cat copies. That is about 2.5% of a 4×1 step, the largest software-only gain left there. A single all_to_all_single does not remove those copies. Across nodes, the network sets the floor. Halving the bytes (bf16 spectra) or overlapping transposes with compute are the only levers, and both change numerics or need torch-harmonics work.

Where a 4×1 step goes

Top CUDA time in one profiled baseline step (logs/prof-sp4x1-base.txt): spectral-contraction bmm 1.31 s, conv/1×1 GEMMs about 1.2 s, aten::copy_ 0.73 s, distributed-transpose all_to_all 0.30 s, gradient comms 0.38 s. The 0.73 s of copies (contiguous around the SHT transposes) is the next optimization target. bf16 autocast was 15% slower on 1×4, because the spectral path upcasts.

Multi-node scaling

Data-parallel replicas of a 4-GPU tile group across nodes. With TCP NCCL, 2 nodes took 18.2 s/step. With the OFI plugin, the small model runs 2.0–2.4 s on 2 nodes against 1.99 s on one. A 2.1 B-parameter run first looked like a hang: it was the model build. torch-harmonics precomputes Legendre weights on CPU, and on nodes busy with the copy and stats jobs that took over 5 minutes against 40 s on an idle node.

With the OFI plugin and DDP gradient sync, 4×1 tiles per node scale almost perfectly: the baseline runs 4.26 s/step on 1 node and 4.24–4.25 s on 2 and 3 nodes. The old per-parameter hooks cost 2.5% more across nodes. Splitting tiles across nodes scales poorly: 4×2 over 2 nodes is only 9% faster than 4×1 on one, and 4×3 over 3 nodes only 16%. The “(htf-ignored)” rows were meant to be 0.5 modes, but my new builder field overrode the benchmark’s patch, so they ran the full baseline.

Open issues

  • Production is not submitted. scripts/sbatch-train-hr.sh is ready (8 nodes, 48 h, self-requeue) but has only passed sbatch --test-only. The choice of 0.5 modes is set in the config and is yours to confirm.
  • No restart checkpoint on SIGTERM under spatial parallelism. A walltime requeue resumes from the last checkpoint_every_n_batches save, so set that interval to fit the walltime.
  • Writers and map aggregators have no spatial gather and may save only the root tile. The power spectrum is skipped under spatial parallelism.
  • Slow SHT setup. The Legendre precompute takes about 40 s per model build at lmax 720 on one CPU thread, and much longer on a busy node. It runs on every start and requeue.
